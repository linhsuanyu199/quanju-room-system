# 第三方支付串接可行性評估

**評估對象**：短租排房系統（quanju-room-system）
**日期**：2026-09-02
**結論先講**：技術上完全可行，但**目前的純前端架構做不到**，必須先增設一支後端 Function。這是唯一的硬性前置條件。

---

## 一、為什麼現在做不到

系統目前是「純靜態前端 + Supabase」：`index.html` 直接在瀏覽器裡跑，沒有任何自己的伺服器程式。

所有金流服務商（綠界、藍新、PayPal 皆同）都要求交易參數必須用**商店密鑰**在伺服器端簽章後才送出。密鑰一旦放進前端，任何人按 F12 檢視原始碼就能拿到，等同於把收款帳戶的印章交出去，可以偽造任意金額的付款成功通知。

因此不論選哪一家，第一步都一樣：**先建立一支後端 Function 保管密鑰並負責簽章與驗簽**。

### 建議的後端落點

| 方案 | 說明 | 適合度 |
|---|---|---|
| **Supabase Edge Function** | 已在用 Supabase，密鑰用 `supabase secrets set` 存放，與現有 `company_id` 租戶隔離天然整合 | **推薦** |
| Netlify Function | 估價站（quanju-pricing）已經在用同樣模式，經驗可複製 | 次選 |
| 自架伺服器 | 要自行處理維運、憑證、備份 | 不建議 |

推薦 Supabase Edge Function 的關鍵理由：付款成功後要寫回訂單狀態，Edge Function 可以用 `service_role` 直接寫資料庫，不必再繞一層 API。

---

## 二、三家比較

> **重要**：以下費率與撥款週期為市場慣行的概略範圍，**實際條件依簽約時的合約為準**，且會依商家的月營業額級距、產業別而異。簽約前請直接向業務索取正式報價單，不要以本文件數字做財務試算。

### 綠界科技 ECPay

| 項目 | 內容 |
|---|---|
| 支援方式 | 信用卡（含分期／定期定額）、ATM 虛擬帳號、超商代碼、超商條碼、行動支付 |
| 所需金鑰 | `MerchantID`（商店代號，可公開）、`HashKey`、`HashIV`（**兩者必須存後端**） |
| 簽章方式 | 參數排序後串接 HashKey/HashIV → URL encode → SHA256 → 產生 `CheckMacValue` |
| 測試環境 | 有完整的測試商店與測試卡號，可在不動用真錢的情況下跑完整流程 |
| 撥款週期 | 信用卡約 T+7～T+30；ATM／超商通常較短。依合約級距而定 |
| 費率 | 信用卡約 2.x%；ATM 與超商多為每筆固定手續費 |
| 文件品質 | 中文文件齊全，有官方 SDK（PHP/.NET/Node 等），台灣中小企業採用率最高 |

### 藍新金流 NewebPay

| 項目 | 內容 |
|---|---|
| 支援方式 | 與綠界大致相同，另有電子錢包整合 |
| 所需金鑰 | `MerchantID`、`HashKey`、`HashIV`（同樣必須存後端） |
| 簽章方式 | 交易參數以 AES-256-CBC 加密成 `TradeInfo`，再對其做 SHA256 產生 `TradeSha` |
| 測試環境 | 有測試環境 |
| 撥款週期 | 與綠界同一量級，依合約而定 |
| 費率 | 與綠界同一量級，實務上兩家可互相議價 |
| 文件品質 | 中文文件齊全 |

**綠界 vs 藍新**：對本系統而言技術難度與整合工作量幾乎相同，差別只在加密演算法細節。**選擇應以費率議價結果與撥款速度為準，不是技術考量。** 建議兩家都問過再決定。

### PayPal

| 項目 | 內容 |
|---|---|
| 支援方式 | 國際信用卡、PayPal 餘額 |
| 所需金鑰 | `Client ID`（可公開）、`Client Secret`（必須存後端）、Webhook ID |
| 簽章方式 | OAuth2 取 access token → 呼叫 Orders API；回調用 Webhook 簽章驗證 |
| 撥款週期 | 入 PayPal 帳戶為即時，但**提領到台灣銀行帳戶另需作業日與提領手續費** |
| 費率 | 跨境交易費率明顯高於本地方案，另有幣別轉換價差 |
| 適用情境 | **只有在有外籍房客、需收外幣時才值得做** |

**評估**：短租房客若以本地客為主，PayPal 的投入產出比低。建議列為第二階段，先做綠界或藍新其中一家。

## 三、後端 Function 需要實作的端點

不論選哪一家，後端要開的端點是同一組四支：

### 1. `POST /pay/create` — 建立付款單
- 輸入：`booking_id`、金額、付款方式
- 動作：
  - 驗證呼叫者的 JWT，取得 `company_id`
  - **金額必須由後端從資料庫的訂單重新計算**，不可信任前端傳來的金額（否則可被竄改成 1 元）
  - 寫入一筆 `payments` 記錄，狀態 `pending`，產生自己的 `merchant_trade_no`
  - 用密鑰簽章，回傳要 POST 到金流商的表單參數
- 輸出：表單參數（前端自動 submit 導向金流商付款頁）

### 2. `POST /pay/callback` — 接收付款結果（伺服器對伺服器）
- **這是整個串接最關鍵的一支**，也是唯一能相信的付款成功來源
- 動作：
  - **驗簽**：用 HashKey/HashIV 重算檢查碼，不符就直接拒絕。跳過驗簽等於任何人都能偽造「已付款」
  - **冪等處理**：金流商會重送通知，同一筆交易重複收到時不可重複記帳。用 `merchant_trade_no` 做唯一鍵
  - 更新 `payments` 狀態為 `paid`，並回寫訂單付款狀態
  - 回應金流商指定的成功字串（綠界為 `1|OK`），否則對方會持續重送

### 3. `GET /pay/return` — 使用者付款完成後導回的頁面
- **只用於顯示畫面，絕對不可以用這支的參數去改資料庫狀態**（使用者可自行偽造網址參數）
- 實務做法：導回後只顯示「處理中」，實際狀態讀資料庫（由 callback 寫入）

### 4. `POST /pay/refund` — 退款
- 需要管理員權限（`role='admin'`）
- 寫入退款記錄，狀態機為 `paid → refunding → refunded`

### 資料表建議

新增 `payments` 表，欄位至少包含：
`id`、`company_id`、`booking_id`、`merchant_trade_no`(unique)、`gateway`、`method`、`amount`、`status`、`gateway_trade_no`、`raw_callback`(jsonb)、`created_at`、`paid_at`

RLS 沿用既有 `get_my_company_id()` 模式：使用者只能讀自己公司的付款記錄；寫入一律由 Edge Function 以 `service_role` 執行。

## 四、退款與對帳流程

### 退款
1. 後台管理員在訂單頁按「退款」，填金額與原因
2. Function 驗證：該筆為 `paid` 狀態、退款金額 ≤ 已付金額、呼叫者為 admin
3. 呼叫金流商退款 API
4. **信用卡退款有時間限制**：超過一定天數（通常是當期請款結帳前）只能做「取消授權」，之後只能走「退刷」，兩者 API 不同、到帳時間也不同。這點要在 UI 上對管理員說明，否則會一直有人問「為什麼錢還沒回來」
5. ATM／超商付款**無法原路退回**，只能人工匯款。系統要能記錄「人工退款」這個類型

### 對帳
1. 金流商每日提供對帳檔（可下載或用 API 拉）
2. 建議做一支排程（GitHub Actions cron 或 Supabase pg_cron）每日比對：
   - 我方 `payments` 表中 `status='paid'` 的當日總額
   - 對帳檔中的當日總額
   - **差異列出來給人看，不要自動修正**。金額對不上一定是有事情發生，自動修正會把問題蓋掉
3. 另外要處理「幽靈交易」：使用者付了款但 callback 沒收到（網路異常）。做法是對 `pending` 超過 30 分鐘的付款單，主動呼叫金流商的查詢 API 補正狀態

## 五、申請所需文件

**共通前提：必須是公司或商號，個人身分無法申請。**

| 文件 | 說明 |
|---|---|
| 公司設立登記表 / 商業登記抄本 | 經濟部核發 |
| 統一編號 | |
| 負責人身分證正反面 | |
| 公司存摺封面影本 | **戶名必須與公司名稱完全一致**，用個人帳戶會被退件 |
| 公司大小章 | 用印於申請書 |
| 營業項目 | 需涵蓋所販售的服務。短租／住宿相關若不在登記項目內，可能需要先變更登記 |
| 網站／App 資料 | 需可正常開啟，且必須有**服務條款、隱私權政策、退換貨（退訂）條款、聯絡方式** |

### 特別提醒（容易卡關的兩點）

1. **審核會看網站內容**：金流商會實際打開網站檢查。目前 `public.html` 與 `terms.html` 已有基礎，但**退訂政策**（提前退租如何計費、押金如何處理、多久前取消可全額退款）需要明確寫出來，否則審核容易被退。

2. **短租／住宿可能被列為需補件產業**：部分金流商對住宿業會要求提供**旅館業或民宿登記證**。若房源屬於代管的一般住宅，這點需要在洽談初期就先問清楚，避免投入開發後才發現無法過審。這是本案最大的商務風險，**建議在寫任何一行程式碼之前先確認**。

## 六、建議的推進順序

1. **先打電話問綠界與藍新業務兩件事**：(a) 短租代管業態能否過審、需要什麼證照；(b) 索取正式費率與撥款條件報價
2. 兩家都能過審 → 比價後選一家；都不能過審 → 本案暫停，改走匯款＋人工核銷（可先在系統內做「付款狀態」欄位管理）
3. 選定後：補齊網站的退訂條款 → 送件申請 → 取得測試環境金鑰
4. 開發：建 `payments` 表與 RLS → 實作四支端點 → 用測試卡號跑完整流程（含付款、逾期、退款、重複 callback）
5. 上線前必做：把 callback 端點的驗簽與冪等處理各寫一組測試，這兩個地方出錯是直接的金錢損失

## 七、風險摘要

| 風險 | 影響 | 對策 |
|---|---|---|
| 密鑰外洩 | 可偽造交易，直接財損 | 只存後端環境變數，絕不進 git、絕不進前端 |
| 未驗簽的 callback | 任何人可偽造「已付款」 | callback 一律驗簽，驗不過直接丟棄 |
| callback 重複 | 重複記帳、重複退款 | `merchant_trade_no` 唯一鍵 + 冪等處理 |
| 前端傳金額 | 可竄改成 1 元 | 金額一律後端重算 |
| 產業無法過審 | 整個功能做不成 | **開發前先確認**（見第五節） |
