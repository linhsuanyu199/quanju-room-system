# 金流上線清單

程式碼已經寫完了，但**現在線上還收不到錢**，因為沒有金流商的金鑰。
這份文件寫的是「從現在到真的能收款」中間剩下的事，以及每一步的理由。

目前收的是什麼錢：**向使用這套系統的業者收訂閱費**（月繳／年繳）。
不是代收房客租金 —— 那條路需要「代收代付」資格，是另一個量級的事，
不在這次範圍內。

## 二、要向金流商業務問什麼

申請前先問清楚，不要先送件再發現不適用。按重要性排序：

1. **「短租／旅宿管理 SaaS 訂閱費」這個業態你們收不收？**
   短租／住宿常被列為需補件或高風險產業。重點是講清楚
   「我們收的是軟體月費，不是住宿費、不代收房客的錢」——
   這兩件事的審查標準完全不同。
2. **審核要哪些文件？** 一般是：公司登記（或商業登記）、負責人身分證、
   公司帳戶存摺封面、網站網址。先問清楚省一輪往返。
3. **費率與入帳週期**：信用卡大約 2.x%，ATM／超商是固定手續費。
   入帳是 T+N？有沒有最低請款金額？
4. **有沒有定期定額（自動續扣）？** 現在的設計是「每期自己來付一次」。
   要做自動續扣得改成訂閱型 API，欄位 `subscriptions.gateway_sub_id`
   已經留好位置了。先問有沒有、再決定要不要做。
5. **測試商店（stage）怎麼申請？** 免費，而且第四節一定要用到。
6. **統一發票**：金流商有沒有代開發票的加值服務？
   不然收了錢還要自己開票，會變成每月的人工作業。

## 三、要設哪些環境變數

全部設在 **Vercel → Settings → Environment Variables**。
repo 是**公開**的，這些值永遠不可以進 git。

| 變數 | 說明 |
| --- | --- |
| `SUPABASE_SERVICE_ROLE_KEY` | **必填**。沒有它 `/api/pay/*` 全回 503。Supabase → Settings → API |
| `PUBLIC_BASE_URL` | **必填**，如 `https://quanju-room-system.vercel.app`（結尾不要斜線）。綠界的通知網址由它組出來 |
| `ECPAY_MERCHANT_ID` | 綠界商店代號 |
| `ECPAY_HASH_KEY` | 綠界 HashKey |
| `ECPAY_HASH_IV` | 綠界 HashIV |
| `ECPAY_ENV` | `stage`（預設）或 `prod`。**沒有明確設成 `prod` 就是打測試站**，這個預設方向是刻意的 |
| `PAY_ALLOW_MOCK` | 選填。設 `1` 才會啟用假金流 |

三個 `ECPAY_*` 金鑰**要嘛三個都設、要嘛都不設**。
程式判斷「有設金流」的條件是三個都有值——設一半比完全沒設更危險，
會讓使用者走到綠界的頁面才看到 CheckMacValue Error。

### 假金流（`PAY_ALLOW_MOCK=1`）

假金流會直接開通訂閱，等於免費升級，所以上了兩道鎖：

1. 環境變數 `PAY_ALLOW_MOCK=1`
2. 呼叫者必須是 `is_platform_admin()`

兩個條件同時成立才會啟用。單靠環境變數太脆弱——
有人手滑在 production 設了它，就等於開放任何人免費升級。

**綠界金鑰一旦設好，假金流就自動失效**（程式先看有沒有真金流），
不需要記得回來關掉它。

## 四、最重要的一步：先用測試商店驗 CheckMacValue

`api/_lib/ecpay.js` 的簽章演算法有兩個地方是**照文件描述還原的，
不是靠執行驗證的**：

1. 參數排序規則（不分大小寫的字母序）
2. URL encode 模仿 .NET `HttpUtility.UrlEncode`
   （不編碼 `-_.!*()`，把 `'` 編成 `%27`、`~` 編成 `%7e`、空白編成 `+`）

`scripts/test-pay.js` 能測「我們自己簽的自己驗得過」、
「改一個字就驗不過」，但**測不出「我們算的和綠界算的一樣」**——
那需要綠界的金鑰才能比對。這兩點只要有一個對不上，
綠界就回「CheckMacValue Error」，而且訊息不會告訴你哪裡錯。

所以流程是：

1. 申請綠界**測試商店**（免費）
2. Vercel 設 `ECPAY_ENV=stage` ＋ 測試商店的三個金鑰
3. 在系統裡按「月繳」，看是否順利進到綠界付款頁
   （進得去 = 送出去的 CheckMacValue 對了）
4. 用綠界提供的測試卡號完成付款
5. 看 `payments` 表那筆有沒有變成 `paid`
   （變了 = **收回來**的通知也驗簽成功了，兩個方向都通了）
6. 看 `subscriptions` 的 `current_period_end` 有沒有往後推
7. 只有以上全部通過，才把 `ECPAY_ENV` 改成 `prod` 並換上正式金鑰

**不要跳過第 3～6 步。** 測試商店是免費的，省下的那半小時
會在正式上線時用客訴還回來。

## 五、刻意沒做的事（以及為什麼）

### 線上退款 API
退訂閱的情境很少，而且幾乎都夾著客訴或特殊條件。
現在走人工：`admin_set_subscription()` 調整方案與到期日，
退款在金流商後台手動辦。等到退款變成每週都要做的事再自動化。

### 主動向金流商查單對帳（幽靈交易）
會發生這種情況：使用者付了錢，但綠界的通知因為網路問題一直沒送達，
我方永遠停在 `pending`。這叫幽靈交易，真正的解法是我方**主動**
用金流商的查詢 API 核對每一筆 `pending`。

那需要金鑰，所以現在做不了。目前只有 `pay_expire_stale()`
（每天把超過 3 天的 `pending` 收成 `expired`），那是**清場，不是對帳**。
3 天這個數字是因為 ATM／超商繳費碼本來就可能幾天後才繳。

→ **拿到金鑰之後要補的第一件事就是這個。**

### 自動續扣
見第二節第 4 點。現在每期要自己來付一次，到期前的提醒靠
`applySubUI()` 的橫幅。

### 發票
沒有任何開票功能。先問金流商有沒有代開服務（第二節第 6 點）。

## 六、安全設計摘要（code review 時對照用）

| 風險 | 防線 |
| --- | --- |
| 前端改金額 | `pay_quote()` **沒有金額參數**。金額從 `plans` 表算。不是多一道檢查，是讓它在結構上不存在 |
| 偽造付款成功 | 只有驗過 `CheckMacValue` 的伺服器通知能銷帳。`pay-done.html` 完全不寫入 |
| 前端直接改 `payments` | `revoke insert, update, delete ... from authenticated, anon`。前端只能讀自己公司的 |
| 重複通知 → 重複加月份 | `pay_mark_paid()` 用 `for update` 鎖列 ＋ `status='paid'` 早退 |
| 回放攻擊（攔到通知無限重送） | 同上。驗簽本身防不了回放，防線在資料庫的冪等 |
| 成員偷偷幫公司下單 | `/api/pay/create` 用**使用者自己的 token** 問 `is_company_admin()`，不是用 service_role 問 |
| 金額對不上就自動開通 | 標成 `mismatch` 並**停止**開通，轉人工。錢的事對不上，寧可讓人介入也不要讓系統猜 |
| ATM 取號被誤判成失敗 | `RtnCode=2`（取號成功）維持 `pending`，不標 failed |
| 失敗通知蓋掉已付款的單 | `pay_mark_failed()` 遇到 `status='paid'` 直接忽略 |
| 金鑰洩漏 | 金鑰只在 Vercel 環境變數，不在資料庫（任何能讀 `pg_proc` 的人都看得到函數內容）、不在 git |
| 設定只設一半 | 三個 `ECPAY_*` 要全有才算有設；`ECPAY_ENV` 預設 `stage` |
